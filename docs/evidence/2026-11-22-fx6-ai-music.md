| Part | File |
|---|---|
| Generation, guards, storage, reuse, record | `services/clip/music_gen.py` |

The runtime folder is never in code: env `UJWALAM_ACESTEP_RUNTIME`, else `paths.acestep_runtime` in the gitignored
local profile. Not set on this laptop yet: putting the runtime folder into the local profile makes it a private term,
and the private scan then flags the existing handover that names that folder. Open question for the user: let the
scan ignore `paths.acestep_runtime` (a rule change), or set the folder another way. Until then the source is off here.

## Real runtime run (once, off air)

`live-check: off air`, no process under the installed app folder, nothing else on the GPU. Env
`UJWALAM_ACESTEP_RUNTIME`, `HF_HUB_OFFLINE=1`, `HF_HUB_DISABLE_TELEMETRY=1`; nothing was downloaded. The test
`RealRuntimeTests.test_one_real_track` called `music_gen.make` with the default guards (real `on_air`, real
`nvidia-smi`, real heavy-job lock). Whole-GPU memory sampled every 0.5 s from outside.

| Item | Value |
|---|---|
| Target | energy 0.9, moods phonk/edm/trap -> phonk, 140 BPM, 30 s |
| Free GPU memory before | 5262 MB (desktop 659 MB used) |
| Model load (in the child) | 11.0 s |
| Generation | 5.4 s |
| Whole call (child start to analysed track) | 17.7 s |
| torch peak | 4246 MB |
| Whole-GPU peak | 5497 MB of 6141 MB |
| Result | `made`, 30.0 s WAV, stored with its JSON (caption, seed 863402770, revisions, licence note) |
| Measured tempo | 70.31 BPM (half time of the asked 140) |

The test then failed on its tempo check (70.31 vs 140). Fix after the run: `tempo_fix` doubles or halves the measured
tempo when that lands within 3 % of the asked tempo (70.31 -> 140.62), and keeps the measured value as `bpmMeasured`.
The fix is unit-tested; the real run was not repeated (one run allowed).

Free-memory floor: the brief asked for 5.5 GB free, which this card never has (6141 MB total, about 660 MB for the
desktop). The floor is 5000 MB (job about 4.85 GB plus margin); see D429.
